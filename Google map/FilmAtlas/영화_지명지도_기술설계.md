# 영화 공간 아카이브 → 지명 추출 → 구글맵 서비스
## 상세 기술설계 문서

작성일: 2026-06-28
대상: 수천 편 영화의 "공간 초록(Spatial Abstract)" 텍스트를 지명 단위로 분석해 지도 위에 배치하고, 이용자가 지도를 탐색하다 특정 지역에 도달하면 그 지역에 연결된 글의 제목·본문 일부를 보고 클릭해 전체를 읽는 웹 서비스.

---

## 0. 결론 먼저

**가능합니다. 그것도 지금 기술로 충분히, 그리고 합리적인 비용으로 가능합니다.**

이 프로젝트는 사실 세 개의 잘 알려진 기술 문제의 조합입니다.

1. **지오파싱(Geoparsing)** — 글에서 지명을 찾아내고(인식), 그 지명이 실제 지구상 어디인지 좌표로 확정(해소)하는 일. 학계·산업에서 성숙한 분야이고, 2025년 기준 최신 방법은 **LLM으로 지명을 인식하고 + 지명사전(gazetteer)·지오코딩 서비스로 좌표를 확정**하는 하이브리드입니다.
2. **지오코딩(Geocoding)** — 지명 문자열을 위경도로 변환. 구글 Geocoding API가 그대로 해줍니다.
3. **지도 시각화 + 탐색 UX** — 수천~수만 개 지점을 지도에 얹고, 화면(viewport) 안에 들어온 지점만 목록·말풍선으로 보여주는 "지도+목록 연동" 패턴. 에어비앤비·부동산 앱이 쓰는 바로 그 방식입니다.

핵심은 새 기술을 발명하는 게 아니라, **이미 검증된 블록들을 올바른 순서로 연결**하는 것입니다. 아래에 그 연결 방법을 단계별로 설계했습니다.

## 1. 전체 아키텍처 한눈에

```
[ 수천 개 .md 영화 텍스트 ]
            │
            ▼
┌─────────────────────────────────────────┐
│  ① 추출 파이프라인 (1회성, 배치 처리)        │
│  Gemini 2.5 (structured output)          │
│  → 글마다 지명 목록 + 지명 단위(scale) +     │
│    문맥 + 제목 + 발췌(excerpt) JSON 생성    │
└─────────────────────────────────────────┘
            │
            ▼
┌─────────────────────────────────────────┐
│  ② 지오코딩 + 정제                          │
│  Google Geocoding API → 위경도            │
│  + 캐시(중복 지명 재요청 방지)               │
│  + 모호성/가상지명 처리                      │
└─────────────────────────────────────────┘
            │
            ▼
┌─────────────────────────────────────────┐
│  ③ 데이터 저장                             │
│  GeoJSON 파일 + Firestore/BigQuery        │
│  (지점 ↔ 영화글 다대다 관계)                 │
└─────────────────────────────────────────┘
            │
            ▼
┌─────────────────────────────────────────┐
│  ④ 웹 지도 프론트엔드 (이용자가 보는 화면)      │

```

①②③은 **여러분 컴퓨터(또는 클라우드)에서 한 번 돌리는 데이터 가공 단계**이고, ④만 인터넷에 상시 떠 있는 서비스입니다. 이 구분이 비용·운영 난이도를 크게 낮춥니다.

## 2. 단계 ① — 지명 추출과 "단위" 규명 (가장 중요한 단계)

### 2.1 왜 단순 NER이 아니라 LLM인가

전통적 NER(spaCy, 구글 Cloud Natural Language API의 LOCATION 엔티티)도 지명을 뽑긴 합니다. 하지만 여러분 데이터에는 두 가지 까다로운 특성이 있습니다.

- **단위(scale)가 제각각**: "바르셀로나"(도시), "산타 콜로마"(구), "지중해"(바다), "거리 이름", "어느 아파트" 등 행정 단위가 섞여 있습니다.
- **문학적·은유적·가상 지명**: 영화 텍스트에는 실재하지 않거나 상징적인 장소가 섞일 수 있습니다.

전통 NER은 "이게 장소다"까지만 말하고, **단위가 뭔지, 실재하는지, 어떤 맥락인지**는 말해주지 않습니다. 2025년 연구 합의는 명확합니다 — **LLM이 지명 인식과 맥락 분류에서 기존 NER·BERT를 크게 앞섭니다.** 특히 구글 생태계를 쓰기로 하셨으니 **Gemini 2.5의 구조화 출력(Structured Output)**이 정답입니다. JSON 스키마를 주면 그 형식에 맞는 결과를 보장합니다.

### 2.2 Gemini에게 글마다 뽑게 할 항목 (출력 스키마)

각 영화 글 1편당 아래와 같은 JSON을 받습니다.

```json
{
  "film_title": "Biutiful",
  "language": "EN",
  "summary_excerpt": "본문 첫 2~3문장 발췌 (지도 말풍선용)",
  "places": [
    {
      "name_raw": "Santa Coloma de Gramenet",
      "name_canonical": "Santa Coloma de Gramenet, Barcelona, Spain",
      "scale": "district",          // country/region/city/district/street/poi/natural/fictional
      "is_real": true,
      "mention_count": 3,
      "context_snippet": "그 지명이 등장한 문장",
      "role": "main_setting"        // main_setting / passing_mention / symbolic
    }
  ]
}
```

**`scale`(단위) 분류**가 바로 여러분이 말한 "지명의 단위는 다르지만"을 해결하는 태그입니다. 이 한 필드로 나중에 지도에서 "도시 단위만 보기", "거리 단위까지 보기"를 줌 레벨에 따라 켜고 끌 수 있습니다.

### 2.3 정확도를 위한 핵심 기법

- **장소를 만들어내지 않게(hallucination 방지)**: 프롬프트에 "원문에 실제로 등장한 표현만 추출하고, `name_raw`는 원문 그대로 인용하라"를 명시. 추출 후 `name_raw`가 원문에 실제로 존재하는지 문자열 검증으로 한 번 더 거릅니다.
- **단위·실재 여부 동시 판정**: 위 스키마처럼 `scale`과 `is_real`을 같이 뽑아, 가상·상징 지명은 지도에 다르게 표시(또는 제외)합니다.
- **배치 처리**: 수천 편이면 Gemini Batch API(비동기, 더 저렴)로 야간에 한 번에 돌립니다.

## 3. 단계 ② — 지오코딩 (지명 → 좌표)

추출된 `name_canonical`을 위경도로 바꿉니다.

### 3.1 도구: Google Geocoding API

구글 생태계 활용 방침에 맞고, 품질·다국어 커버리지가 최상급입니다.
- **2026년 가격(2025-03 개편 후)**: Geocoding은 Essentials 등급으로 **월 10,000건 무료**, 초과분 1,000건당 약 **$5** 수준.
- 수천 편 × 평균 지명 수십 개라 해도, **중복 지명 캐싱**을 적용하면 실제 지오코딩 호출은 보통 수천~2만 건 이하로 떨어집니다. 즉 **1회성 비용 0~수만 원** 수준입니다.

### 3.2 비용·정확도를 동시에 잡는 캐시 전략

같은 "바르셀로나"가 200편에 나와도 좌표는 한 번만 구하면 됩니다.
```
지명 문자열 → (캐시에 있으면 재사용) → 없으면 API 호출 → 캐시에 저장
```
이것만으로 API 호출이 80~95% 줄어듭니다.

### 3.3 모호성·특수 케이스 처리

- **동명이지(같은 이름 다른 곳)**: Geocoding 호출 시 `name_canonical`에 상위 행정구역(국가·도시)을 붙여 보내면 대부분 해소됩니다. Gemini가 ②.2 단계에서 이미 상위 맥락을 채워두므로 시너지가 납니다.
- **가상/상징 지명(`is_real:false`)**: 좌표를 매기지 않거나, 영화의 대표 촬영지/배경 도시에 "상징 핀"으로 묶습니다.
- **자연지물(바다·산맥)**: 점이 아니라 영역이라 좌표 1개로는 부정확. 대표점(centroid)만 쓰거나 별도 레이어로 분리.
- **무료·오픈 대안**: 비용을 0으로 묶고 싶으면 **Nominatim(OpenStreetMap)**로 지오코딩 가능(가격 무료, 단 사용량 제한·정확도 트레이드오프). 1회성 대량 처리는 로컬에 OSM 데이터를 띄워 무제한 처리하는 방법도 있습니다.

## 4. 단계 ③ — 데이터 저장 구조

지점과 글은 **다대다 관계**입니다(한 글에 여러 지점, 한 지점에 여러 글). 두 가지 산출물을 만듭니다.

1. **`places.geojson`** — 지도가 직접 읽는 파일. 각 지점 feature에 좌표 + 그 지점에 연결된 글들의 ID·제목·발췌를 담습니다.
2. **글 본문 저장소** — 전체 본문은 무겁기 때문에 지도에 미리 다 싣지 않고, 클릭 시 불러옵니다.
   - 단순하게: 글마다 정적 HTML/JSON 파일 (Firebase Hosting/Cloud Storage).
   - 검색·필터가 필요하면: **Firestore**(글·지점 메타데이터, 실시간 조회) 또는 대량 분석이면 **BigQuery**.

**추천(구글 스택, 비개발자 친화)**: 메타데이터·관계는 Firestore, 정적 자산(geojson·본문)은 Firebase Hosting. 운영 서버 없이 거의 무료 한도 안에서 돌아갑니다.

## 5. 단계 ④ — 웹 지도 프론트엔드 (이용자 경험의 핵심)

여러분이 묘사한 UX("지도를 네비게이션하다 특정 지역에 가면 그 글들이 제목·발췌로 보이고, 클릭하면 읽는다")는 **"지도 + 화면연동 목록 + 말풍선"** 패턴입니다.

### 5.1 화면 구성

```
┌───────────────────────────┬───────────────┐
│                           │  [이 지역의 글] │
│        지 도 (메인)         │  • Biutiful    │
│   ● 클러스터(숫자)           │    "발췌문..."  │
│      ● ● 핀들               │  • Import/Export│
│         📍 (클릭→말풍선)      │    "발췌문..."  │
│                           │  ...(스크롤)    │
└───────────────────────────┴───────────────┘
   지도를 움직이면 → 우측 목록이 화면 안 지점들로 자동 갱신
   핀 클릭 → 제목+발췌 말풍선 → "전체 읽기" → 본문 패널 슬라이드
```

### 5.2 동작 원리

- 지도가 멈출 때마다 **현재 화면 경계(bounds) 안에 있는 지점만** 골라 우측 목록을 갱신합니다. 이게 "특정 지역에 가면 그 글들이 보인다"의 정체입니다.
- 핀을 누르면 그 지점에 연결된 글들의 **제목 + 발췌**가 말풍선에, "전체 읽기"를 누르면 본문을 불러와 패널에 띄웁니다.

### 5.3 수천~수만 핀 성능 문제 → 클러스터링

지점이 많으면 다 찍을 수 없습니다. 멀리서 보면 "이 지역에 글 87개" 같은 **클러스터 원**으로 묶고, 줌인하면 풀립니다. 줌 레벨에 따라 ②.2의 `scale` 태그로 "지금은 도시 단위만" 같은 필터도 겁니다.

### 5.4 지도 라이브러리: 두 가지 선택지

| 항목 | **Google Maps JavaScript API** | **MapLibre GL JS** (오픈소스) |
|---|---|---|
| 구글 생태계 정합 | ★★★ (Geocoding과 한 콘솔) | ★★ (지오코딩만 구글, 지도는 별도) |
| 비용 | 지도 로드(Dynamic Maps) 월 10,000회 무료, 초과 1,000회당 ~$7 | 지도 렌더링 **무료**(타일만 별도) |
| 트래픽 늘면 | 이용자 많아질수록 과금↑ | 거의 고정비, 대규모에 유리 |
| 마커 클러스터링 | 공식 라이브러리 제공 | 내장(GeoJSON 클러스터) |
| 디자인 자유도 | 보통 | 매우 높음(스타일 완전 제어) |
| 비개발자 난이도 | 낮음(문서·예제 풍부) | 중간 |

**권고**: 우선 **Google Maps JS API로 PoC**를 만드는 걸 추천합니다(여러분 방침과 정합, 학습자료 풍부, Geocoding과 한 프로젝트에서 관리). **이용자 트래픽이 커져 지도 로드 비용이 부담되면 그때 MapLibre로 프론트만 교체**하면 됩니다 — 데이터(geojson·Firestore)는 그대로 재사용되므로 교체 비용이 작습니다. 이 "데이터와 표현 분리" 설계가 핵심입니다.

## 6. 최종 추천 스택 (구글 중심, Claude가 코드 작성 전제)

| 단계 | 추천 도구 | 비고 |
|---|---|---|
| 지명 추출·단위분류 | **Gemini 2.5 (Structured Output, Batch)** | JSON 스키마 보장, NER보다 정확 |
| 지오코딩 | **Google Geocoding API** + 캐시 | 무료 한도 + 캐싱으로 비용 최소화 |
| (무료 대안) | Nominatim/OSM 로컬 | 비용 0, 대량 1회 처리용 |
| 데이터 저장 | **Firestore** + **Firebase Hosting** | 서버리스, 거의 무료 |
| 지도 프론트 | **Google Maps JS API** → (확장 시 MapLibre) | 클러스터링 라이브러리 사용 |
| 호스팅·배포 | **Firebase Hosting** (또는 Cloud Run) | 정적+서버리스, HTTPS·CDN 기본 |

전부 구글 콘솔 한 곳(Google Cloud + Firebase)에서 관리되고, 무료 한도 안에서 PoC가 가능합니다.

## 7. 비용 추정 (대략, 2026년 기준)

**1회성(데이터 가공)**
- Gemini 추출: 수천 편 배치 처리 — 글 길이에 따라 보통 **수천 원~수만 원**.
- 지오코딩: 캐싱 적용 시 호출 수천~2만 건 → 무료 한도(월 1만) 안팎, **0~수만 원**.

**상시(서비스 운영)**
- Firebase Hosting/Firestore: 트래픽 적으면 **무료 한도 내(월 0원)**.
- Google Maps 지도 로드: 월 방문이 만 단위를 넘기 전까지 **무료**. 초과 시 1,000 로드당 약 $7 → 트래픽 커지면 MapLibre로 전환해 사실상 고정비화.

즉 **초기엔 거의 0원으로 시작**, 인기를 끌면 그때 비용이 생기고, 그 시점에 오픈소스로 갈아타 통제할 수 있습니다.

## 8. 단계별 로드맵 (제작 방법)

**1단계 — 개념검증(PoC), 1~2일**
샘플 영화 5~10편으로 ①추출 → ②지오코딩 → `places.geojson` 생성 → 구글맵에 핀+말풍선 표시. "정말 글이 지도에 뜨고 클릭해 읽힌다"를 눈으로 확인.

**2단계 — 파이프라인 자동화**
수천 편 전체에 Gemini 배치 추출 + 캐시 지오코딩을 한 번에 돌리는 스크립트. 결과 검수(가상지명·오지오코딩 샘플 점검).

**3단계 — 프론트엔드 완성**
클러스터링, 화면연동 목록, 본문 패널, 줌별 `scale` 필터, 검색/영화제목 필터.

**4단계 — 배포·운영**
Firebase Hosting 배포, 도메인 연결, 사용량 모니터링. 트래픽 추이 보고 필요 시 MapLibre 전환.

**5단계(선택) — 자율 에이전트화**
새 영화 글을 폴더에 넣으면 자동으로 추출→지오코딩→지도반영까지 도는 파이프라인(스케줄 작업). 여러분이 말한 "에이전트가 스스로 처리"를 운영 단계에서 구현.

## 9. 미리 짚는 난제와 해결책

| 난제 | 해결책 |
|---|---|
| 지명 단위가 제각각 | Gemini가 `scale` 태그 부여 → 줌 레벨별 표시 제어 |
| 동명이지(같은 이름 다른 곳) | 상위 행정구역 맥락을 붙여 지오코딩 |
| 가상·상징 지명 | `is_real` 플래그로 분리 표시 또는 대표지에 묶기 |
| 한 지점에 글이 수십 개 | 클러스터 + 목록 스크롤 + 발췌 우선 표시 |
| 수만 핀 성능 | 클러스터링 + 화면 경계 내 지점만 렌더 |
| 다국어(EN/원어 혼재) | Gemini가 언어 감지·정규화, Geocoding 다국어 대응 |
| 비용 폭증 우려 | 캐싱 + 무료 한도 + (확장 시) MapLibre 전환 |
