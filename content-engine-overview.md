# FilmCurio content engine — architecture & rationale (read this to understand the missions)

This explains **how FilmCurio's content is produced and published, and *why* it's built this way** —
the reasoning behind `SPEC.md` §3.2 / §3.3 and the enhancement-pack missions. Read this for the
mental model; read `SPEC.md` for exact fields/routes and `AGENTS.md` for the terse standing rules.
If anything here conflicts with SPEC, SPEC wins.

---

## 1. Mental model (one paragraph)
The **website (Next.js on Vercel) only ever reads `published` rows** from Supabase. All content is
produced by **background worker loops** that run *outside* the website and talk to it **only
through Supabase** (tables + a job queue). The seam is the database, not the web runtime. **The
core design point:** a film's featured Q&A is generated in **one model call** (not a multi-stage
graph), with quality enforced *inside* that call and by **post-publish auditing** — there is **no
separate verifier/scorer and no review queue**. A single human **admin** oversees from `/admin`.

## 2. The content lifecycle (state machine + buffer)
```
draft  →  approved (publish buffer)  →  published
   ↘ rejected (invalid after one retry)          ↘ hidden (unpublished after the fact)
```
- **draft** — just generated by AI. Not public.
- **approved** — passed the **deterministic validator**; ready, but deliberately **not yet live.**
  Sits in the **publish buffer** until the publisher releases it. Not public.
- **published** — live. **Only `published` rows are publicly readable (RLS) and in the
  sitemap/JSON-LD.** This gate keeps drafts off crawlers/AI fetchers.
- **rejected** — a film whose call couldn't return valid output even after one retry (logged,
  skipped). **hidden** — pulled after publication by the admin.

**There is no `in_review` state and no human/second-model review step.** Quality is enforced (a)
**inside the generation call** — the model self-checks accuracy/sourcing and **drops or rewrites
weak items before returning them**, attaching a `self_confidence` per item — and (b) by a
**deterministic validator** (pure code) before anything becomes `approved`.

Why a buffer: it **decouples making content from releasing it**, which (a) lets us generate in big
efficient batches while publishing slowly, and (b) builds a backlog so the site keeps publishing on
days the generator doesn't run.

Every item carries **provenance**: `source` (human/ai), `generated_by` (model), the **editorial
lens** (`answerer_lens`/`asker_lens`), `self_confidence`, `scheduled_for`, `published_at`. Every
state change writes a **`content_events`** audit row.

## 3. The worker loops

### Loop 1 — Generator (autonomous, list-driven, **single-call**)
The admin **uploads a curated film list once** (~1,000 titles); an importer resolves each to TMDB
and marks it `in_pipeline`. A **daily scheduler runs on its own** — no per-film manual trigger —
working through the list. Per film:
- **One call → up to 10 featured Q&A.** The **single-call prompt** (`prompt-featured-qa.md`)
  returns the questions real viewers most want answered about *that* film, each with an optional
  short **body** (the asker's elaboration), an **answer** that leads on the question's crux and
  lands one **"aha"**, an **asker/answerer lens**, a named `aha`, `self_confidence`, and
  `claims_sourced` — as strict JSON. The model **self-checks and drops/rewrites weak items in-call.**
  No planner, no separate drafter/verifier/scorer stages.
- **Validate (deterministic, no LLM).** Parse the JSON; require valid schema, **≥8 items** each
  with question+answer (body optional), film title echoed, **`self_confidence` ≥ 0.75**,
  `claims_sourced = true`, intra-film dedupe, a banned-term/safety regex, length sanity. Pass →
  write as `draft`. Hard failure → **one retry of the call**, then skip + log. **This validator is
  the whole gate.**
- **Linkify (deterministic).** Wrap the **first mention** of each known catalogue film/director in
  an internal link (the model only names films; it never writes URLs).
A **model router** maps the call to a model via **admin-tunable config** (`pipeline_config`);
swappable without code changes. Run via the **Batch API** with the system/persona block
**context-cached** (identical across films) — ~**1,000 calls cover ~10k posts** cheaply.

### Loop 2 — Publisher (cadence engine)
A **light, frequent, jittered** job releases `approved` items to `published`:
- **Each entity has its own `scheduled_for`** — the question, the canonical answer, and each
  reading publish on **independent** timings, not as a bundle.
- **Ordering rule:** the question goes live first, then (after a gap) its canonical answer, then
  its readings spaced over hours/days. An answer never publishes before its question.
- **Jitter:** random gaps (not fixed ticks), no identical timestamps, no bursts; daily volume
  ±jitter under a **daily cap + slow ramp**.
- `published_at` is the **real release time — never backdated.**
- On release: ISR-revalidate the affected pages + update the sitemap.

Why: a burst of dozens of simultaneous AI posts/day is a recognizable bot footprint. Spreading
releases is **sane editorial cadence + risk reduction, not disguise.** Pacing is *not* a substitute
for quality — see §6.

### Loop 3 — Curiobot (media auto-embedding — **per film**)
Attaches **one media set per film**, shared by all of that film's questions (not one lookup per
question — keeps Curiobot's calls ~10× lower). Two paths: **at generation** (when the film's Q&A
are produced) and a **~3-hour sweep** that finds **published films/questions lacking media**.
- **Images = TMDB only** (posters/backdrops/stills, with attribution). No web scraping / "Google
  Images", no user uploads — both are copyright/DMCA risk.
- **Video = YouTube official embed + Data API search** (trailers, video essays, interviews).
  **Match on film identity** (exact title + year + director), not loose keywords — reject videos
  matching only a generic word, and **attach nothing below the confidence threshold** (junk media
  is worse than none; the live build wrongly attached space/asteroid clips to *Stalker* — that's
  the failure this prevents). Prefer official/reputable channels; reject reaction/clickbait.
- **Automated relevance + spoiler/appropriateness filter.** Admin moderates **after the fact.**
- **Placement:** a **"Related on YouTube" module at the bottom of the question** (see
  `ref-question-media.html`), video via a **click-to-load facade**. `ImageObject`/`VideoObject`
  JSON-LD for the search surface.

## 4. The website's role
Pure consumer: SSR/ISR reads `published` rows, renders pages + JSON-LD (the GEO layer), and on
revalidate picks up newly published/edited content. It never generates, validates, or runs the
loops.

## 5. Authorship & voices
- AI content is attributed to a **transparent editorial identity — FilmCurio Editorial** —
  surfaced with a **lens** label. The voices are the **10 asker + 10 answerer lenses** embedded in
  the single-call prompt (`prompt-featured-qa.md`): general-audience → cinephile *question* voices,
  and critic-grade *answer* voices that vary in tone, not in rigour. They are original/anonymized
  temperaments, **never named after or made identifiable as a real critic**, and **never posing as
  independent members of the public.** (`editorial-voices.md` holds the earlier voice notes; the
  live canonical set is the lens roster in the prompt.)
- The **lens is fixed at creation** (stored as provenance), independent of when the publisher
  releases the item.
- **Canonical answer** = the house-bylined hero per question; **contributions** = individual
  readings (a lens, or a real user).

## 6. The hard rules (and why) — never violate
- **No sockpuppets / no fake engagement.** The lenses are **transparent editorial voices, not user
  accounts**; never fabricate human-looking accounts, AI upvotes, fake "other readers", or fake
  reputation. It deceives users, breaks fake-review rules, and triggers the exact search/AI spam
  penalties the GEO strategy depends on avoiding. Upvotes/contributions/reputation are real users
  only.
- **No backdating.** `published_at` is the true release time. Pacing ≠ faking history.
- **Quality > volume.** ~1,000 films × ~10 ≈ 10k pages is a *scaled-content-abuse* risk. The
  conservative rate cap, slow ramp, dedup/thin-content checks, and **post-publish spot-audit** are
  core requirements. The dominant signals are quality, uniqueness, helpfulness, and (later) real
  engagement + links — not timing tricks.
- **Published-gate everywhere.** draft / approved / hidden never reach anon clients, sitemap, or
  JSON-LD.
- **TMDB-only images; spoiler-guarded media.**
- **Honest disclosure.** There is **no pre-publish human or second-model review**; `/about` and
  per-page disclosure say exactly that — *AI-written, self-checked as written, published directly,
  audited after publication.* **Never claim per-item human review.**
- **The moat is the editorial standard**, encoded in the single-call prompt: pick the questions
  people actually ask, **answer the exact crux**, land one real **"aha"**, stay **film-specific and
  accurate** (E-E-A-T top grade). The model is a tool; the standard is the product.
- **Approval mode** for auth, secrets/keys, SQL migrations/RLS, robots, deploy, and the first
  production batch.

## 7. Observability (how to watch it)
Three sources feed the `/admin` **Activity Log**:
- **`jobs`** — one row per film run (status, current step, counts, cost, timestamps).
- **`agent_activity`** — a per-worker heartbeat ("what it's doing right now", today's counts).
- **`content_events`** — the timestamped audit trail of every step
  (generated / validated / published / audited / failed).
The Activity Log shows **Now** (heartbeat), a **Timeline** (events + links), and **Latest outputs**
(newest drafts + published).

- The admin console (6b) is the **control plane + audit surface** for all loops.

## 9. Glossary
- **Buffer** — the `approved` state: validated content waiting to be released.
- **Generator / Publisher / Curiobot** — the three decoupled loops (make / release / enrich).
- **Canonical answer** — the single house-bylined hero answer per question.
- **Contribution / reading** — an individual answer by one editorial lens (or a real user).
- **Editorial lens** — a disclosed, anonymized question/answer voice from the single-call prompt;
  never a real critic, never a fake user.
- **Self-gate** — the in-call self-check: the model drops/rewrites weak items and reports
  `self_confidence`.
- **Validator** — the deterministic code gate (schema, ≥8, `self_confidence ≥ 0.75`, dedupe,
  safety) that **replaces the old verify/score/review stages**.
- **Jitter** — randomized publish timing to avoid a bot-burst footprint.
- **Provenance** — `source` / `generated_by` / lens / `self_confidence` on each row.
