## ✅ 2026-08-03 갱신 — 수동 조치 없음이 확인됨 (오너 직접 확인)

GSC → 보안 및 수동 조치, 종 아이콘 메시지 **0건**. 이 문서 §2 항목 #1이 종결됐다.

**의미:** 구글의 인적 제재는 없다. 재심사 요청은 적용 대상이 아니고, 해서도 안 된다.
남아 있던 "P≈0.10" 분기가 사라졌으므로 **이 문서의 나머지 진단이 유일한 설명으로 확정**된다 —
강등이 아니라 신규 사이트 1회성 크롤·샘플링 창의 만료 + 07-16 본인의 noindex 배포.

**실행상 함의:** "구글이 우리를 벌하고 있다"는 가설에 배정할 시간은 이제 0이다.
남은 문제는 오직 **크롤 수요**(외부 인기)와 **자작 피해 복구**뿐이다.

### C1 — 무엇이 실제로 있었나

가장 결정적인 사실 하나로 무너집니다. **사이트는 2026-06-17에 색인 가능해졌습니다.**

```
git: 2026-06-17 11:26 "LAUNCH: SITE_INDEXABLE=true + sitemap lists readings & tropes"
GSC 최초 데이터일 = 06-17.  06-17:0  06-18:0  06-19:2  06-20:2 … 07-07:28
```

| 구간 | 일수 | 노출/day |
|---|---|---|
| 06-17 → 07-07 (발견) | 21 | ~1.5 |
| 07-08 → 07-17 ("기준선") | 10 | 94 → 663 → 507 |
| 07-20 → 07-31 ("바닥") | 12 | ~21 |

"507/day 기준선"은 **평지가 아니라 8일짜리 단조 상승 구간**이고, "바닥" 21/day는 상승 구간 이전의 **14배**입니다. 평탄한 구간이 기록 어디에도 없습니다. 강등되려면 먼저 랭크된 코퍼스가 있어야 하는데, 이 사이트는 그걸 가져본 적이 없습니다.

직접 측정 결과는 더 명확합니다.

- **사이트 평균 순위: 붕괴 전 19.46 → 붕괴 후 16.05 (개선)**
- 붕괴 후(07-20~08-02) 노출을 받은 157페이지 중 **97개(62%)가 07-20 이전에 한 번도 노출된 적 없는 신규**이고, `columbus-2017/reception`은 **39노출 @ 평균순위 2.5, 'Submitted and indexed'** 로 데뷔했습니다.
- 우리 대표 증거였던 `gattaca-1997`은 **생애 전체에서 노출이 있었던 날이 4일**이고, **07-16과 07-17에 이미 0**이었습니다. 마지막 날 순위 10, 첫날 순위 10.
- 붕괴 전 노출이 있던 1,507페이지 중 **921개(61%)가 단 하루, 308개(20%)가 이틀**. 열흘 이상 살아남은 페이지는 **4개**. 98.9%가 07-08 이후 처음 등장.
- 메커니즘 5/5 확인: 각 URL의 노출 창이 **자기 크롤 날짜**에 열립니다(07-07 크롤 → 07-08 노출, 07-13 크롤 → 07-13 노출). 공통 날짜에 켜진 스위치가 없습니다.

"110개국 균일"과 "web+image+video 동시"도 아티팩트입니다. 붕괴 전 114개국 중 **46개국(40%)이 노출 ≤3**이었고 미국이 4,096 중 1,690(41%)이었습니다. 1~3을 들고 있던 나라는 총량이 94% 떨어지면 산술적으로 0이 됩니다. 이미지·비디오는 **생애 총 노출이 각각 256, 255**이고 07-08/09 이전엔 정확히 0이었습니다 — 셋 다 같은 한 번의 발견 버스트입니다.

그리고 07-16 커밋 `56759a66`(prune thin surfaces to noindex)이 **붕괴 전 노출의 51.5%**를 직접 건드렸습니다(reception 27.9% + misreadings 9.7% + takescore 7.1% + tv 1.9% + atlas 5.0%). 하락은 배포가 반영되기 전에 이미 시작돼 있었습니다: 663(07-14) → 560 → 458.

**실무적 함의가 큽니다.** "강등"이면 페널티·재심사·HCU 코호트의 22개월 회복 기저율이 적용됩니다. 실제로 일어난 건 **초기 색인 선정 실패(failed initial index selection)** 입니다. 다른 문제이고, 다른 처방이 필요하며, "12~24개월 구글 손절"의 근거로는 쓸 수 없습니다. 나쁜 소식도 같이 있습니다 — **재심사 같은 빠른 경로도 없습니다.**

### C2 — 크롤은 멈춘 적이 없고, 계측기가 고장나 있었습니다

`mt_crawler_visits`(마이그 0081 자체 비콘) 기준. 다른 크롤러 전부가 대조군입니다.

| 날짜 | **Googlebot** | bingbot | Applebot | Yandex |
|---|---|---|---|---|
| 07-17 | **119** | 100 | 456 | 159 |
| 07-20 | **71** | 123 | 420 | 234 |
| 07-24 | **20** | 114 | 387 | 225 |
| 07-31 | **10** | 121 | 332 | 199 |
| 08-02 | **12** | 122 | 360 | 222 |

빙·애플·얀덱스는 완전히 평평합니다. 구글만 움직입니다. 비콘 결함·WAF·사이트 가용성 전부 배제됩니다. 그리고 **어제(08-02 23:18) 도 크롤했습니다** (`66.249.64.0/24` → `/locations/china/shanghai`).

계측기 고장의 결정적 증거:

```
Googlebot이 /film/city-lights-1931 을 2026-07-29 16:55:24Z 에 fetch, Vercel 프로덕션 로그 = 200
같은 URL, 오늘 GSC URL Inspection = coverage 'URL is unknown to Google', lastCrawl = None
```

즉 **"unknown to Google / lastCrawl=never"는 fetch 이력이 아니라 색인 멤버십에 대한 진술**입니다. `/now` 8건의 `lastCrawlTime=never`와 "26개 중 84% unknown" 표본은 크롤에 대해 아무것도 증명하지 않습니다.

`/now` 기사가 안 잡힌 진짜 이유는 발견 실패이고, 타임스탬프가 정확합니다.

```
/sitemaps/now.xml   lastDownloaded = 2026-07-17T13:54Z   submitted = 25   indexed = 0
  → 그 순간 DB: published 19 + digest 5 + /now 자체 = 정확히 25.
  → 07-25~07-29 발행 14편은 구글이 읽은 사이트맵에 한 번도 들어간 적이 없음.
/news-sitemap.xml   lastDownloaded = 2026-07-09T02:05:48Z  (제출 1.8초 후, 그 이후 25일간 0회)
```

정정 2건: `/now` 신규는 **8편이 아니라 14편**이고, **07-15 01:01 ~ 07-25 07:40 사이 10일간 아무것도 발행되지 않았습니다** — now.xml이 아직 수집되던 기간에는 새 콘텐츠 자체가 없었습니다.

### C3 — 유명세 가설은 통계적으로 죽었습니다

유명세 층화 무작위 표본 114개(영화 메인 50 / 감독 24 / locations 40)를 GSC로 전수 조회:

| 표본 | n | "unknown to Google" |
|---|---|---|
| 영화 메인 | 50 | 47 (94.0%) |
| 감독 | 24 | 20 (83.3%) |
| `/film/locations/` | 40 | 38 (95.0%) |
| **합계** | **114** | **105 (92.1%)** |

크롤되어 평가까지 받은 건 **9개뿐**입니다. C3는 카탈로그의 8%에서 벌어진 현상을 전체의 설명으로 제시한 것입니다. 그 9개 안에서 Mann-Whitney **p = 1.000, 방향은 반대**. 표본 최저 유명세 감독(`yang-woo-suk`, 8,421표 — 경쟁 자체가 없음)은 07-19 크롤 후 **미색인**, 40만표 감독과 28만표 오스카 영화는 색인.

붕괴 전 노출이 있었던 페이지 전체(n=1,142)에 IMDb 표수를 붙여 생존을 회귀하면 **r = +0.0226 (t=+0.76)**, 유명세 십분위별 생존율은 2.6 / 1.8 / 3.5 / 4.4 / 5.2 / 2.6 / 4.4 / 5.3 / 1.8 / 4.3% — 평평하고 단조롭지 않습니다. 기존 7개 표본도 `roman-polanski`(204만표, 이 랭킹의 기준점)가 **크롤된 적이 없어** 제외해야 하고, 남은 6개는 **p = 0.133**입니다.

**바뀌는 처방:** 개별 페이지를 더 깊게 써서 색인 경쟁에서 이기려는 작업은 의미가 없습니다. 이유가 "경쟁에서 진다"가 아니라 **"구글이 가져간 적이 없다"** 이기 때문입니다. 레버는 페이지 품질이 아니라 발견/크롤 수요입니다.

### Gate 0에서 나온 부수 사실 3가지

1. **07-16에 504 1,292건 + 404 3,187건**이 있었습니다. 기존 진단이 07-17부터 봤기 때문에 하루 차이로 놓쳤습니다. "5xx 배제"는 과장이었습니다. 크롤율 계단 하강(119 → 71@07-20 → 20@07-24 → 7@07-29)이 5xx 이벤트(07-16, 07-27/28)를 뒤따르는 건 **시사적이지만 미증명**입니다(07-24 계단 앞엔 5xx가 없음).
2. **07-29~31 폭풍**은 Supabase가 Cloudflare **521 "Web server is down"** 을 반환한 총체적 DB 장애였고, 그동안 사이트는 **최소 11,812개(추정 ~30,000개)의 고유 URL에 404**를 캐시로 뿌렸습니다. 07-30 하루에 404 41,692 + 504 103,941. **07-29 이후에 측정한 모든 GSC 판독은 해석 불가능**합니다.
3. 다만 **붕괴 창(07-18~28) 자체의 자작 404는 70개 표본 중 1개(1.4%), 전체 ~20개**입니다. 07-18 당일 총 404는 539건으로 07-14/15 기준선(~530)보다 낮았습니다. 자작 피해는 붕괴의 원인이 아닙니다.

**현재 상태(08-03 24시간):** 504 = 3,880 / 128,003 = **3.0%**. 응급은 아니지만 목표 1% 위입니다. **남은 504의 62%가 `/credits/[person]` 한 라우트(2,411건)** 입니다.

## 3. 버릴 것

**1) A등급 410 전량 — 특히 `/movies-like`, `/whereto`.**
24일간 비구글 검색 유입 217건 중 115건(52.9%), 30일 창에서는 58.7%가 이 두 군에 떨어집니다. 유일하게 **성장 중인** 채널(6.4/day → 19.9/day, 주간 3배)의 절반 이상을 되돌릴 수 없게 삭제하는 작업입니다. 기대 구글 이득은 0입니다. 게다가 계획서 Week 1의 자체 안전장치("Bing 노출 5% 초과 계열은 90일 유지")가 이미 이 작업을 금지하고 있습니다 — 표와 단서 조항이 서로 모순입니다.

**2) B등급 noindex 15,000 — reception(붕괴 전 노출 28.0%, 지금도 18.9%), credits(12.9%), takescore/film.**
빙·DDG·얀덱스도 `noindex`를 똑같이 존중합니다. "noindex + 200 계속 서빙"은 빙에서도 제거됩니다. 대가로 얻는 것은 이름 붙일 수 있는 구글 시스템도, 성공/실패를 구분할 관측치도 없는 채널입니다.

**3) "크롤 버짓" 논리 전부.**
Googlebot은 히트 순위 5위이고, 히트의 37%가 `/robots.txt`입니다. 용량 한도 근처가 아닙니다. 구글 문서가 명시적으로 "한도에 닿지 않으면 이전되지 않는다"고 말합니다. 이 논리가 등장하는 모든 문장을 지워야 합니다.

**4) 818페이지 오리지네이터 업그레이드를 "구글 회복 레버"로 두는 것.**
`/film/locations/*` 중 **역대 한 번이라도 구글 노출을 받은 슬러그가 68개**뿐이고, 그중 818 keep-set 안에 있는 건 **38개**입니다. 20시간을 들여 95%가 한 번도 노출된 적 없는 페이지를 다듬는 일입니다. (문서 자체 §6이 인정하듯 이 핀들은 타인의 촬영지 보도를 인용한 것이라, 벗어나려던 집계 패턴 그 자체이기도 합니다.)

**5) "데이터셋 배포 (Week 3)" — 이미 07-13에 완료됐습니다.**
HF `wonwooyoon/metatake-filming-locations`: 다운로드 45, 좋아요 0, 인바운드 링크 0. Zenodo: 조회 3, 다운로드 3. 3주치 실측입니다. 성장 레버로 재계획하지 말고, **정합성 수정**으로 재분류하십시오 — 현재 공개된 건 "17,341 locations / 1,917 films"(출처 없는 상위집합)인데, DB의 출처 보유 핀은 4,443개입니다.

**6) "Week 3-4: iOS 서명 자격증명 복구 — 저장소 최대 레버" — 이미 해결됐습니다.**

## 4. "대부분의 의미 있는 것들이 올라올까?"

정면으로 답합니다. **아니요. 그리고 그건 잃은 게 아니라 애초에 가진 적이 없습니다.**

### 계획의 정의상 천장

살아남는 C등급 ~2,400페이지는 붕괴 전(07-09~07-17, 9일간) 총 **668 노출 = 74 노출/day**를 벌었습니다. **이 페이지들이 자기 최고 상태를 100% 되찾아도 74 노출/day, 3% CTR로 약 2 클릭/day입니다.** 이게 절단 계획이 성공했을 때의 상한입니다. 실패했을 때가 아니라 성공했을 때입니다.

그리고 "돌아온다"는 표현 자체가 부정확합니다. 붕괴 전 노출이 있었던 1,507페이지 중 61%는 **단 하루** 등장했습니다. 되돌아갈 상태가 존재하지 않습니다. 있는 건 "처음으로 선택되기"뿐입니다.

### 구속 조건

Googlebot 페이지 fetch ≈ **6~8건/day**(12/day 중 37%가 robots.txt). 이 속도로 현재 25,126 URL을 한 번 훑으려면 **8.6년**입니다. 2,400으로 줄여도 **1패스 = 10개월**입니다. 절단은 이 숫자를 개선하지 않습니다 — 용량 한도에 닿아 있지 않기 때문입니다.

### 3 / 6 / 12개월 기대치

기준선: 현재 구글 노출 **~19~21/day**, 클릭 ~0.6/day, 07-20~08-02에 노출을 받은 페이지 **157개**.

## 4. Root cause of the storm — not a code bug, a dependency outage

Runtime errors on 07-30 show the actual failure:

```
GET /film/downfall-2004 500
  Error: {"message":"<title>supabase.co | 521: Web server is down</title>
   ... jvgarcqrtsmgfimdcwgo.supabase.co ... 2026-07-30 13:02:41 UTC"}
GET /film/locations/vengeance-is-mine-1979 504
  Vercel Runtime Timeout Error: Task timed out after 300 seconds
```

**Supabase was returning Cloudflare 521 "Web server is down."** Every fail-closed path fired simultaneously. The code paths are real bugs, but they were triggered by a total database outage, not by ordinary flakiness.

I confirmed a **third** fail-closed path beyond the two in the brief — and it is worse than either:

`lib/film-credits-data.ts:105-112` — `if (!film || !film.tmdb_id) return null; ... if (!movie) return null;` where `movie` comes from `tm()`, which is `fetch(...).catch(() => null)` and `if (!r || !r.ok) return null`. So `/film/[slug]/credits` 404s on **any TMDB hiccup**, never checks `visible` at all, and caches for 86400s. That is the 2,700 distinct credits 404s.

## 5. Error-derived noindex (task 5)

**The direct measurement does not exist.** Vercel full-text log search over 07-29→08-01 returns "window exceeds retention"; Supabase logs are 24h only. The RPC error rate during the storm is unrecoverable.

What is recoverable is the **exposure**, and it is larger than the brief assumed. Four callers pass **no `visible` hint** and therefore have zero protection from `filmGate.ts:50-52`:

```
app/film/[slug]/_shared.tsx:706        ← THE FILM MAIN PAGE
app/film/lineage/[slug]/page.tsx:205
app/film/[slug]/reception/page.tsx:234
```

The code comment claims the `visible:true` short-circuit "keeps a transient RPC error from de-indexing a live film's established subpages." **It does not protect the film main page itself** — the site's primary indexable surface — which calls `filmMainIndexable(slug)` bare.

Across a ~72-hour outage that is up to ~860 re-bake opportunities per film page, each one a coin flip on whether `noindex` gets written into the ISR HTML. And the RPC is not cheap — `explain analyze` gives **427ms warm with 2,466 disk reads**, so it is among the first things to time out under saturation.
