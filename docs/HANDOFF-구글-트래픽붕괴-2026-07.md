## 0. 한 줄 결론

구글은 2026-07-18~19에 metatake.net에 **사이트 단위 순위 강등**을 걸었다.
색인에서 빠진 것만의 문제가 아니다. **색인이 살아있는 페이지조차 노출이 −93%**다.

페이지에 있었고, 가지치기는 오히려 색인 페이지를 2,729 → 4,641로 늘렸다.
GSC 알람은 규모를 말해주지 않는다 — 07-28 "중복 페이지" 알람의 실체는 **2페이지**다.

## 2.1 "내가 7/18에 noindex를 많이 걸어서 벌받은 건가" — 아니다 (2026-08-03, GSC Coverage 수출로 재확인)

오너가 반복해서 떠올리는 질문이라 근거를 여기 박아둔다. 출처는 GSC의
`metatake.net-Coverage-2026-08-03.zip`(차트·심각한 문제 CSV)과, 붕괴 직전 노출
보유 페이지의 **현재 robots 상태 라이브 확인**이다.
⚠️ zip 내부 파일명이 EUC-KR이라 `unzip`은 "Illegal byte sequence"로 실패한다 —
파이썬 `zipfile`로 열고 UTF-8 플래그(`flag_bits & 0x800`)가 없으면
`cp437 → euc-kr`로 재디코딩해야 한다.

**재실행 도구: `worker/gsc-noindex-attribution.py`** (인자 없이 돌리면 07-18 사건).
다음에 같은 질문이 나오면 이 절을 다시 쓰지 말고 스크립트를 돌릴 것:
```
python3 worker/gsc-noindex-attribution.py
python3 worker/gsc-noindex-attribution.py --pre 2026-09-01:2026-09-07 \
                                          --post 2026-09-15:2026-09-21 --top 100
```

### 결정적 증거 — 잃은 노출의 72%는 지금도 색인 가능한 페이지의 것

붕괴 직전 주(07-11~17) 노출 상위 **250개** 페이지를 오늘 직접 가져와 `meta robots`를 봤다
(전체 1,359페이지 중 노출 기준 59%를 덮는다).

| 현재 상태 | 페이지 | 붕괴 전 노출 |
|---|---|---|
| **200, noindex 없음 (색인 가능)** | **155** | **1,639 (67%)** |
| 200, NOINDEX | 49 | 412 (**17%**) |
| 308 리디렉션 (atlas→locations 개명 잔재) | 46 | 404 (**16%**) |

⚠️ **표본 크기에 민감하다 — 초판(상위 60개)의 "72% / 13%"는 과소추정이었다.** 상위로 갈수록
noindex 비율이 낮다. 250개 기준이 더 정확하고, 더 넓히면 noindex 몫은 더 오를 수 있다.
`--top` 을 키워 재확인할 것.

**⚠️ 재검증 문서의 "51.5%"와 충돌하지 않는다 — 재는 대상이 다르다.**
`docs/HANDOFF-재검증-최종정리-2026-08-03.md` §C1은 07-16 커밋 `56759a66`이 **건드린 URL 계열**의
노출 비중을 센다(reception 27.9 + misreadings 9.7 + takescore 7.1 + atlas 5.0 + tv 1.9 = 51.5%).
이 절은 **오늘 실제로 noindex인 URL**을 센다. 두 값이 갈리는 이유는 (a) 가지치기가 계열 전체가
아니라 영화별 게이트로 걸려서 같은 `reception`도 색인 가능한 것이 섞여 있고(`ahed-s-knee`=indexable
vs `licorice-pizza`=NOINDEX), (b) `atlas` 5.0%는 noindex가 아니라 **308**이라 위 표의 별도 행으로
빠지기 때문이다.

**합산하면 우리 배포에 귀속되는 몫은 noindex 17% + 리디렉션 16% = 약 33%다.** "noindex가 원인이
아니다"는 결론은 유지되지만(67%가 여전히 색인 가능), **"13%"라고 축소해 말해서는 안 된다.**

```
/tropes                                     60 → 0   [200 indexable]
/film/the-blair-witch-project-1999/credits  57 → 0   [200 indexable]
/movies-like/immaculate-2024                52 → 0   [200 indexable]
/film/locations/the-piano-1993              46 → 0   [200 indexable]
/locations/tunisia                          30 → 0   [200 indexable]
```

태그는 그대로인데 구글이 안 보여준다. §1.4와 같은 결론을, 이번엔 **개별 URL의
라이브 robots**로 독립 확인했다. 전체로도 동일: 노출 페이지 1,359 → 92(−93%),
노출 4,166 → 131(−97%).

## 3. 남은 설명 — 사이트 단위 품질 강등

관측된 서명:

1. 특정 주말(07-18~19)에 **모든 표면 동시** 하락
2. 재크롤 없는 대량 색인 탈락
3. 색인 생존 페이지의 노출 −93% (순위 강등)
4. 크롤 예산을 주요 엔진 중 최저로 축소
5. 기술적 결함 0, 타 엔진 정상

이건 개별 페이지 평가가 아니라 **도메인 신뢰도 평가**다.

이 사이트의 프로필:
- 도메인이 구글 색인에 등장한 지 **약 4주**
- `films` 생성 이력: 06-17 400편, 06-18 992편, 06-25 4,744편, 07-03 274편
- 약 2,000편 × 서브페이지 12종 ≈ **25,126 URL을 6주 만에 발행**
- 브랜드 검색 수요 **0건** (A·B 양 구간 모두 "metatake" 쿼리 0)

구글 입장에서 이건 "scaled content"의 교과서적 형태다.
07-08~07-17의 노출 상승은 **신규 도메인 시험 기간(허니문)**이었고,
07-18~19에 시험이 끝났다고 보는 게 데이터에 가장 잘 맞는다.

⚠️ **미확인 1건 — 오너만 확인 가능:** GSC → **보안 및 수동 조치 → 수동 조치**.

정확한 확인법 (외부 조사로 확정):
- **"Scaled content abuse"라는 이름의 수동 조치는 없다.** 그건 스팸 *정책* 이름이다.
  실제로 뜨는 항목은 **"심각한 스팸 문제(Major spam problems)"**(앵커 `#pure-spam`,
  본문에 "scaled content abuse" 명시) 또는 **"가치가 거의 없는 빈약한 콘텐츠(Thin content)"**.
  *Site reputation abuse*는 **제3자 콘텐츠** 전제라 해당 없음.
- **"메일 안 왔다"는 근거가 안 된다.** 메일 설정은 사용자별이다. **종 아이콘 → 메시지 패널**을
  12개월·전체 유형으로 봐야 한다. 수동조치 메일은 `[WNC-XXXXXXX]` ID를 단다(WNC-651700=심각한 스팸).
- **"검토 요청" 버튼은 수동 조치·보안 문제에만 뜬다** — 버튼이 없으면 항소할 게 없다는 증거.
- 범위 판별: URL 패턴이 보이면 부분 조치, **"모든 페이지에 영향"** 문자열이면 사이트 전체.
- ⚠️ Glenn Gabe 사례(2026-04-14): **수동 조치는 순위 하락 뒤에 늦게 뜨기도 한다.**
  11일 지난 지금 클린이면 가능성은 크게 낮지만 형식적으로 배제되진 않는다.

### 3.2 ⚠️ 내 진단의 정정 — "재크롤 없이 탈락"은 확정 못 한다

§1.5에서 "구글이 재크롤도 안 하고 색인에서 뺐다"고 썼는데, **이 추론은 안전하지 않다.** 두 가지 이유:

1. **GSC 페이지 색인 보고서가 2026년 6~7월 내내 stale이었다.** 6/11 데이터에서 멈춤 →
   Mueller 7/1 인정 → 7/3 수리(6/29까지) → **다시 멈춤** → 7/23 기준 또 2주째 정체.
   보고 데이터가 뭉텅이(6/13~30, 7/1~10, 7/11~24)로 움직였다.
   내가 본 lastCrawl **7/07~7/14가 정확히 그 stale 구간 안에 있다.**
2. **애초에 lastCrawl로는 판별이 안 된다.** 구글 문서: *"이 도구에 표시되는 모든 정보는
   마지막 크롤 버전에서 파생된다."* 재평가가 있었든 없었든 같은 날짜를 보여준다.
   "색인 파이프라인이 재크롤 없이 재평가한다"는 주장은 **제3자 추론**이지 구글 문서가 아니다.

**→ 재검증 방법: URL Inspection의 "실제 URL 테스트(Test live URL)"** — UI 전용이라 API로는 불가.
오너가 잃은 URL 5~10개에 대해 직접 실행해야 한다.
판독: **라이브 테스트 통과 + 색인 버전 "not on Google" = 기술 문제 아님(품질/중복) = 알고리즘.**
⚠️ 단, 지금은 504가 46%라 **라이브 테스트가 실패할 수 있다** — 그건 §4를 먼저 잡아야 한다는 뜻이다.

**반면 노출 붕괴 자체는 진짜다.** 구글 공식 "Search Console 데이터 이상" 로그에
**2026년 7월 실적 데이터 이상은 없다**(과거 노출 로깅 오류는 2026-04-27 종료). 지금 못 믿을 건
*색인* 보고서지 *실적* 보고서가 아니다.

### 4.1 이게 왜 치명적인가 — 실패가 색인 삭제로 굳는다

두 개의 fail-closed 경로가 일시적 DB 실패를 **다일간 색인 제거**로 변환한다:

- `app/film/locations/[slug]/_shared.tsx:59-69` — Supabase 타임아웃 시 `data: null`이
  "행 없음"과 구분되지 않아 `return null` → `notFound()` → **404**.
  `revalidate = 86400`이라 **24시간 캐시**. DB 타임아웃 한 번이 6위 페이지를 하루 지운다.
  `/film/lineage/[slug]`, `/film/[slug]/credits`도 동일 패턴.
- `lib/filmGate.ts:50-52` — RPC 에러 시 `return false` = **noindex로 fail-closed**.

  DB가 흔들릴 때마다 ISR HTML에 noindex를 구워 넣는다.

지금 40~50% 실패율에서 이 두 경로가 **계속 발화 중**이다.

## 5. 대응 — 우선순위 순

### P0 — 오늘 (전제조건)
구글이 재평가를 하려면 사이트가 응답해야 한다. 504 46%인 사이트는 재평가 대상이 안 된다.

1. **`app/robots.ts` NOINDEX_PATHS 확장** — 크롤 부하의 대부분을 즉시 제거.
   추가 대상: `/film/*/figure/*`, `/takescore/film/*`, `/tv/*`, `/tv/list/*`,
   `/whereto/*`, `/credits/*`, `/catalog/*`.
   전부 이미 noindex이거나 검색 가치가 없는데 크롤 부하 1~5위를 차지한다.
   ⚠️ robots.txt는 루트 파일 계열이라 **워처 자동배포 범위 밖 → 수동 커밋**.
2. **비검색 크롤러 레이트리밋** — Applebot·Yandex·Amzn-SearchBot·미상 "crawler"가
   Googlebot의 **13배**를 먹고 있다. middleware에서 `GOOD_BOT` 외 봇에 스로틀.
3. **fail-closed 2종 수리** — 위 §4.1. `error`를 구분해서 던지고,
   실패 시 `notFound()`/`noindex` 대신 **이전 캐시 유지 또는 503**.
   503은 구글이 "일시적"으로 이해하고 색인을 지우지 않는다. 404·noindex는 지운다.

### P0 — 오늘 (오너만 가능)
4. **GSC → 보안 및 수동 조치 확인.** 결과에 따라 아래 전략이 갈린다.
   - 수동 조치 있음 → 수정 후 **재심사 요청**이 유일한 경로
   - 없음 → 알고리즘 강등, 재심사 요청 불가, §5의 구조 작업만이 방법

### P1 — 1~2주 (구조)
5. **URL 25,000 → 3,000 통합.** noindex가 아니라 **301 통합**.
   영화 1편 = 페이지 1개 원칙. 서브페이지는 섹션/탭으로 흡수.
   **단, 증거 기반으로 남길 것을 고른다** — 붕괴 전 실제로 순위를 받던 표면:
   - **유지**: `/film/locations/*`("where was X filmed" 5~11위, 고유 데이터+출처 있음),
     `/movies-like/*`(6~13위), `/locations/{country}`, `/director/*`, `/now/*`
   - **흡수·삭제**: figure·takescore·credits·q·desk·gallery·meaning·reception 등
     영화당 파생 서브페이지 전부
6. **신규 URL 발행 동결.** 지금 페이지를 더 만드는 건 정확히 반대 방향이다.

### P2 — 기대치 재설정 (가장 중요)
7. **구글 회복을 3~6개월짜리로 잡고, 그 사이 사업을 구글에 걸지 않는다.**
   사이트 단위 품질 강등은 끈적하다. 페이지를 줄인다고 다음 주에 돌아오지 않고,
   통상 **다음 코어 업데이트에서 재평가**된다. 기다린다고 좋아지지 않는다는
   오너의 직감은 맞다 — 단, "아무것도 안 하고 기다리면"이 맞고,
   "구조를 바꾸고 기다리면"은 다르다.
8. **이미 작동하는 채널로 무게를 옮긴다.** Bing·DDG·Ecosia·Yandex·Naver가
   지금 구글의 6배를 보낸다. IndexNow는 이미 라이브. Perplexity·Copilot도 유입 중이고
   MCP 서버·`/api/v1`·컨텍스트팩은 이미 구축돼 있다 — 이쪽이 지금 유일하게 복리가 붙는 곳이다.
9. **북극성은 이미 맞게 잡혀 있다** (`business-strategy-survival`: 주간 재방문자, 동반자 제품).
   브랜드 수요 0건이 구글 강등의 근본 원인 중 하나다. 검색 유입이 아니라
   **직접 수요**를 만드는 게 SEO 회복의 선행조건이지 그 반대가 아니다.

## 5.0 🚨 §5.1의 경로 Disallow 제안은 철회 (2026-08-01 정정)

아래 §5.1에서 `/film/*/figure/*` 등 **경로를 robots.txt로 Disallow** 하자고 썼다. **순서가 틀렸다.**

**robots.txt Disallow는 크롤을 막지 색인을 지우지 않는다.** 제거 대상 URL을 지금 Disallow하면
구글이 그 페이지의 **noindex·410을 영원히 볼 수 없어** 색인에 그대로 남는다. 정확한 순서는:

1. noindex(또는 410)를 서빙하고 사이트맵에서 제거
2. GSC에서 실제로 빠지는 것을 확인 (4~8주)
3. **그 다음에** robots.txt Disallow로 크롤 예산을 회수

지금 robots에 넣어도 되는 건 `/search?*` 같은 **무한 파라미터 공간**뿐이다(이미 들어가 있다).
부하 해소는 **캐싱·사이트맵 축소·기생 크롤러 UA 차단**으로 하는 것이지 경로 Disallow로 하는 게 아니다.

**✅ 실제로 적용한 것(2026-08-01):** 경로가 아니라 **봇 UA 차단**.
`middleware.ts` BAD_UA + `app/robots.ts` LOAD_PARASITES에 5종 추가 —
`meta-webindexer`(9,844히트, 사이트 최대 크롤러, `/credits/*` 순회)·`SleepBot`(1,097)·
`SERankingBacklinksBot`(142)·`AwarioBot`(112)·`AgenstryBot`(39). 전부 **유입 0**.
유지: Googlebot·bingbot(32명)·DuckDuckBot(46명)·Baiduspider·NaverBot·Yandex·
OAI-SearchBot·PerplexityBot, 그리고 **`facebookexternalhit`**(링크 미리보기 페처 —
`meta-webindexer`와 UA·IP 대역(69.171.x)이 다르다. 막으면 공유 카드가 깨진다).
⚠️ Applebot은 **2위 부하(415/일)에 유입 0**이지만 Siri·Spotlight 표면이라 남겨뒀다 — 오너 판단 필요.

## 5.1 P0-1 구체 패치 (⚠️ 경로 Disallow 부분은 §5.0으로 철회됨)

⚠️ 07-31 현재 오너가 DB 과부하를 직접 잡는 중(`9d6ce9be`·`21ff259a`·`fcffb970`·`566d712b`,
작업트리에 `0118_function_memory_tuning.sql` 미커밋). 경합 방지를 위해 **적용하지 않고 제안만** 남긴다.

`app/robots.ts:44`:

```ts
const NOINDEX_PATHS = [
  "/admin", "/api/", "/search?*", "/ask-ai",
  // 2026-07-31 — 크롤 부하 상위 라우트. 전부 이미 noindex이거나 검색가치 0인데
  // 하루 ~140k 요청 중 대부분을 차지하며 DB를 포화시킨다(§4).
  "/film/*/figure/*",   // 3시간 4,564 요청 = 504 1위
  "/credits/*",         // 3시간 2,004
  "/takescore/film/*",  // 이미 noindex (56759a66)
  "/tv/*",              // 이미 noindex
  "/whereto/*",
  "/catalog/*",
];
```

주의:
- `/credits`(목록 랜딩)와 `/credits/*`(인물 개별)는 다르다. 랜딩은 유지할 것.
- `/tv/*`는 `/tv/list/*`까지 함께 덮인다 — 의도된 것(둘 다 noindex).
- robots.txt는 루트 파일 계열 → **워처 자동배포 밖, 수동 커밋 필요**
  (`autodeploy-watcher-scope`).
- Disallow는 색인 삭제가 아니라 크롤 차단이다. 이미 noindex인 페이지를 Disallow하면
  구글이 noindex를 재확인하지 못해 색인에 남을 수 있다 — 하지만 지금은
  **크롤 예산과 DB 생존이 우선**이다. 통합(§5-5)이 끝난 뒤 301로 정리하면 해소된다.

## 5.2 미발견(unknown) 페이지 — 측정과 정정 (2026-08-01)

**측정:**
- 무작위 26 URL(필름메인8·movies-like6·credits6·takescore6): **84%가 "URL is unknown to Google"**.
  구글이 본 4건은 **전부 lastCrawl 07-09** — 사이트맵 제출 직후 1회 패스가 전부.
- **붕괴 이후 발행한 `/now/` 기사 8편(07-25~29): 8편 전부 lastCrawl=never.**
  붕괴 전 기사(07-15~16)는 하루 이틀 만에 색인됐다. → **구글이 신규 URL 수집을 멈췄다.**
- 07-31에 unknown이던 필름 24편, 08-01 재검사에도 **23/24 그대로 unknown**.

**⚠️ "unknown"의 의미 — 내 초기 해석 정정.** Gary Illyes(구글): URL은 *"신호를 모으는 동안 상태 사이를
이동하며, 이 경우 신호가 우리 시스템으로 하여금 그 URL의 존재를 **'잊게'** 만든 것"*.
즉 **unknown = "한 번도 못 봄"과 "봤다가 잊음"이 섞여 있다.** 둘을 분리할 방법은 없다.
(붕괴 이후 생성된 `/now/` 기사는 확실히 전자다.)

**🚨 크롤 예산에 대한 검증 결과 — 하면 안 되는 것들이 확정됐다:**

| 수단 | 판정 | 근거 |
|---|---|---|
| **IndexNow 핑** | **구글에 아예 안 간다** | indexnow.org 참여사 = Bing·Yandex·Naver·Seznam·Yep·Amazon. **구글은 2021년 "테스트하겠다" 이후 도입한 적 없음.** Bing 계열에는 유효 |
| GSC "색인 요청" 버튼 | 도움 안 됨, **부정 신호 가능** | Mueller: 수동 제출에 자주 의존하는 사이트는 *"사이트 전반에 대해 확신이 없다"*는 신호를 보이는 것. *"강력히 권하지 않는다"* |
| 사이트맵 재제출 | 무의미 | Mueller(2026-07-16): *"재제출할 필요 없다"* |
| 발행량 늘리기 | 중립~해로움 | 같은 종류를 더 내면 판정을 강화 |
| 내부 링크 | 내부 우선순위만 | 사이트 전체 수요 천장을 못 올림 |
| **외부 링크·인지도** | **유일하게 문서화된 수요 레버** | 공식 문서: *"인터넷에서 더 인기 있는 URL이 더 자주 크롤된다"* |

**🚨 그리고 가장 중요한 정정 — URL을 줄인다고 크롤 예산이 자동으로 늘지 않는다.**
구글 공식 문서(크롤 예산 관리 가이드) 직접 인용:
> *"다른 페이지를 위해 크롤 예산을 일시적으로 재배분하려고 robots.txt를 쓰지 마라. …
> **구글이 이미 사이트의 크롤 용량 한계에 부딪히고 있는 게 아니라면**, 새로 확보된 크롤 예산을
> 다른 페이지로 옮기지 않는다."*

25,126 → 2,400 통합의 근거는 **크롤 예산 회수가 아니라 ①사이트 전반 품질 인식 ②DB 부하**다.
"페이지를 줄이면 남은 페이지가 더 크롤된다"는 벤더 케이스스터디들은 검증 불가 수치다. 기대하지 말 것.

**→ 실행 함의:** 미발견 84%는 **지금 지우는 데 비용이 0이다**(301·410·제거신호·대기 전부 불필요 —
사이트맵과 내부링크에서 빼면 끝). 반면 구글이 실제로 본 ~16%만 noindex/410 후 4~8주 확인이 필요하다.
통합 작업이 두 트랙으로 갈라지고, 어려운 쪽은 전체의 6분의 1뿐이다.

## 5.3 🔴 504 근본원인 (2026-08-01 워크플로, 8에이전트)

**⚠️ "앱이 주범"과 "크롤러가 주범"이 상충한다 — 미해결.** 오너는 앱 수정 1시간 뒤 504가 멎었다고
보고했고 실제로 멎었다(14:27 UTC 전후). 그러나 포렌식은 외부 크롤러 스윕을 지목한다. 둘 다일 수 있다.

**확정된 사실:**
1. **봇 원장 100배 갭은 측정 아티팩트였다.** `middleware.ts:83-92`의 `seenUA` 10분 dedup(아이솔레이트별)
   때문에 `mt_crawler_visits`는 **요청 수가 아니라 "존재" 카운터**다. UA당 하루 최대 144회가 천장.
   초당 1회 봇과 초당 100회 봇이 같은 숫자를 남긴다. → 원장으로 부하를 추정하면 안 된다.
2. **07-30 12–15 UTC에 140,437 요청 / 504 72,221건.** 같은 창 07-27은 3,551 요청·504 0건.
   상위: `/credits/[person]` **36,326** · `/search` **22,599** · `/network` 10,358(단일 경로).
3. **`/search`를 때리는 미확인 주체가 robots.txt를 무시한다** (`/search?*`는 이미 Disallow인데도).
   `search_all`+`search_semantic`이 DB 시간 4,600초, 호출당 3~4초.
4. **🚨 `/search` 스로틀(`SEARCH_MAX_PER_MIN=20`)이 main에 없다.** 커밋 `86e4ac26`은
   `feat/discovery-feed`에만 있다. 프로덕션은 main에서 빌드된다 → **지금 라이브가 아니다.**
5. **DB 최대 소비자 = `figure_neighbors`** — `pg_stat_statements` 리셋 후 66분 창에서 **총 DB시간의 37.8%**.
   1536차원 brute-force 벡터 스캔이고, **131MB HNSW 인덱스는 한 번도 쓰인 적이 없다.**
6. 프로덕션 트래픽이 **동시 배포 4개**에 쪼개져 있다. `middleware.ts`의 완화장치
   (`blCache`·`seenUA`·`searchHits`)는 전부 **아이솔레이트별 상태**라 배포가 늘수록 비례해 무력해진다.

**→ 다음 폭주는 시간문제다.** 5·4·3이 그대로 살아 있다.
