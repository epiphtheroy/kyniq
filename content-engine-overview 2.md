# Kyniq content engine — architecture & rationale (read this to understand the missions)

This explains **how Kyniq's content is produced and published, and *why* it's built this way** —
the reasoning behind `SPEC.md` §3.2 / §3.3 and the enhancement-pack missions. Read this for the
mental model; read `SPEC.md` for exact fields/routes and `AGENTS.md` for the terse standing
rules. If anything here conflicts with SPEC, SPEC wins.

---

## 1. Mental model (one paragraph)
The **website (Next.js on Vercel) only ever reads `published` rows** from Supabase. All content
is produced by **three background worker loops** that run *outside* the website and talk to it
**only through Supabase** (tables + a job queue). The seam is the database, not the web runtime —
so the heavy/long work never touches the request path, and any agent/framework can play a worker
role as long as it reads the queue and writes rows. A single human **admin** oversees everything
from `/admin`.

## 2. The content lifecycle (state machine + buffer)
Every authored item (question, canonical answer, contribution, media) moves through:

```
draft  →  in_review  →  approved (publish buffer)  →  published
                 ↘ rejected            ↘ hidden (unpublished after the fact)
```

- **draft** — just generated by AI. Not public.
- **in_review** — failed the confidence/appropriateness gate → waits in the **admin queue** for a
  human. Not public.
- **approved** — passed the gate; **verified + ready, but deliberately not yet live.** It sits in
  the **publish buffer** until the publisher releases it. Not public.
- **published** — live. **Only `published` rows are publicly readable (RLS) and in the
  sitemap/JSON-LD.** This gate is what keeps drafts off crawlers/AI fetchers.

Why a buffer: it **decouples making content from releasing it**, which (a) lets us generate in
big efficient batches while publishing slowly, (b) lets a human review before anything goes live,
and (c) builds a backlog so the site keeps publishing even on days the generator doesn't run.

Every item also carries **provenance**: `source` (human/ai), `generated_by` (model), the author
identity, `reviewed_by`, `scheduled_for`, `published_at`. Every state change writes a
**`content_events`** audit row.

## 3. The three worker loops

### Loop 1 — Generator (autonomous, list-driven, multi-model)
The admin **uploads a curated film list once** (~1,000 titles); an importer resolves each to TMDB
and marks it `in_pipeline`. A **daily scheduler then runs on its own** — no per-film manual
trigger — working through the list over days. Per film, a small graph:
- **Planner** — generates the **≥10 questions that arise from the film itself** (what a real
  viewer wonders), deduped. **No category/`question_type` taxonomy** — questions aren't slotted
  into buckets; several may cluster on one theme, and that's fine.
- **Drafter ×N** — writes each question + answer in the **answer-first TL;DR** shape, in a
  **conversational, deep** voice (see §5), as an assigned editorial persona.
- **Verifier ×N (검산)** — a **different model provider/family** fact-checks the *checkable* claims
  (title, year, director, cast, plot) against TMDB and scores confidence. Different family =
  fewer shared blind spots. Interpretation is *not* "verified" — facts + coherence only.
- **Tone/appropriateness** review, then **Kyniqbot** media (Loop 3), then the **Gate**:
  high-confidence + clean → **approved** (buffer); else **in_review** (admin).
A **multi-provider model router** maps each role to a model via **admin-tunable config**
(`pipeline_config`). Models are swappable without code changes.

### Loop 2 — Publisher (cadence engine)
A **light, frequent, jittered** job releases `approved` items to `published`:
- **Each entity has its own `scheduled_for`** — the question, the canonical answer, and each
  reading publish on **independent** timings, not as a bundle.
- **Ordering rule:** the question goes live first, then (after a gap) its canonical answer, then
  its readings spaced over hours/days. An answer never publishes before its question.
- **Jitter:** random gaps (not fixed ticks), no identical timestamps, no bursts; daily volume
  ±jitter under a **daily cap + slow ramp** (volume grows as the site ages).
- `published_at` is the **real release time — never backdated** to fake an organic history.
- On release: ISR-revalidate the affected pages + update the sitemap.

Why: a burst of ~70 simultaneous AI posts/day is a recognizable bot footprint. Spreading
releases is **sane editorial cadence + risk reduction, not disguise** (we stay transparently
editorial). Pacing is *not* a substitute for quality — see §6.

### Loop 3 — Kyniqbot (media auto-embedding)
Attaches relevant media to every question. Two paths: **at generation** (in the buffer, so AI
questions are media-ready at publish) and a **~3-hour sweep** that finds **published questions
lacking media** (esp. human-submitted) and enriches them.
- **Images = TMDB only** (posters/backdrops/stills, with attribution). No web scraping / "Google
  Images", no user uploads — both are copyright/DMCA risk.
- **Video = YouTube official embed + Data API search** (trailers, video essays, interviews);
  prefer official channels; skip embed-disabled.
- **Automated relevance + spoiler/appropriateness filter** (spoilers in titles/thumbnails are a
  real hazard on an interpretation site). Admin moderates **after the fact**.
- **Placement:** a **"Related on YouTube" module at the bottom of the question** (see
  `ref-question-media.html`), video via a **click-to-load facade** (loads the iframe only on
  click → protects performance). `ImageObject`/`VideoObject` JSON-LD for the search surface.

## 4. The website's role
Pure consumer: SSR/ISR reads `published` rows, renders pages + JSON-LD (the GEO layer), and on
revalidate picks up newly published/edited content. It never generates, verifies, or runs the
heavy loops.

## 5. Authorship & voices
- AI content is attributed to **disclosed editorial voices** — a small, fixed set (≈5) of
  **original, anonymized, conversational** personas (`editorial-voices.md`). They are *inspired by
  general critical temperaments*, **never named after or made identifiable as a real critic**.
- **Different voices, different lengths** (short → long), but **every answer opens with a
  standalone, citable claim** (citation-friendly = good for AI engines).
- **The author/voice is fixed at creation** (stored as provenance), independent of when the
  publisher later releases the item.
- **Canonical answer** = one per question, **"Kyniq Editorial" house** byline (the AI-citable
  hero). **Contributions** = individual readings, each by a specific voice — this is where voice
  variety shows.

## 6. The hard rules (and why) — never violate
- **No sockpuppets / no fake engagement.** Never fabricate human-looking accounts, AI upvotes,
  fake "other readers", or fake reputation. It deceives users, breaks fake-review rules, and
  triggers the exact search/AI spam penalties the whole GEO strategy depends on avoiding. AI
  content carries a transparent editorial byline; upvotes/contributions/reputation are real users
  only.
- **No backdating.** `published_at` is the true release time. Pacing ≠ faking history.
- **Quality > volume.** ~1,000 films × ~10 ≈ 10k pages published autonomously is a
  *scaled-content-abuse* risk. The conservative rate cap, slow ramp, dedup/thin-content checks,
  and periodic human spot-check are **core requirements**. The dominant ranking/citation signals
  are quality, uniqueness, helpfulness, and (later) real engagement + links — not timing tricks.
- **Published-gate everywhere.** Drafts/in_review/approved/hidden never reach anon clients,
  sitemap, or JSON-LD.
- **TMDB-only images; spoiler-guarded media.**
- **The moat is the editorial standard**, encoded in the Planner/Drafter prompts: observe the
  film closely before reaching for theory, prefer productive uncertainty to tidy verdicts, keep
  the depth but say it like a person talking. The model is a tool; the standard is the product.
- **Approval mode** for auth, secrets/keys, SQL migrations/RLS, robots, deploy, and the first
  production batch.

## 7. Observability (how to watch it)
Three sources feed the `/admin` **Activity Log**:
- **`jobs`** — one row per film run (status, current step, counts, cost, timestamps).
- **`agent_activity`** — a per-worker heartbeat ("what it's doing right now", today's counts).
- **`content_events`** — the timestamped audit trail of every step.
The Activity Log shows **Now** (heartbeat), a **Timeline** (events + links), and **Latest
outputs** (newest drafts + published) — answering *what is it doing, what did it do, where are the
results.*

## 9. Glossary
- **Buffer** — the `approved` state: verified content waiting to be released.
- **Generator / Publisher / Kyniqbot** — the three decoupled worker loops (make / release / enrich).
- **Canonical answer** — the single house-bylined hero answer per question.
- **Contribution / reading** — an individual answer by one editorial voice (or a real user).
- **Editorial voice** — a disclosed, anonymized, conversational persona; never a real critic.
- **Gate** — confidence/appropriateness check: pass → buffer, fail → admin queue.
- **Jitter** — randomized publish timing to avoid a bot-burst footprint.
- **Provenance** — `source` / `generated_by` / author / `reviewed_by` on each row.
